# Agent instructions — Puzzle

## Project

Browser-based classic picture puzzle (jigsaw-style grid). Players select pieces and place them on a board until the image is complete. Hosted as a static **Progressive Web App** on **GitHub Pages**.

Features beyond the current basics are still being defined — prefer small, incremental changes and confirm product direction before large gameplay redesigns.

## Hard rules

These are project constraints. Follow them unless the user explicitly overrides them.

1. **Vanilla web only** — HTML, CSS, and JavaScript for the shipped app. No React/Vue/Svelte, no bundler, no runtime npm dependencies, no required build step to play or deploy.
2. **GitHub Pages static deploy** — keep a working root `index.html` on `main`. Do not move the app behind a build pipeline without being asked.
3. **ES modules** — app code lives under `js/` and loads via `<script type="module">`. Local preview needs HTTP (`python3 -m http.server`), not `file://`.
4. **Browser storage only** — anything that must persist (progress, settings, preferences) uses **`localStorage`** through `js/storage.js` with namespaced keys (`puzzle:…`). No backend, database, accounts, or cloud sync unless explicitly requested.
5. **Stay modular to reduce merge conflicts** — put new concerns in their own modules/CSS partials. Do not re-merge everything into one giant `game.js` or `styles.css`. Touch the fewest files needed for the task.
6. **Remain a PWA** — keep `manifest.webmanifest`, icons, and root `sw.js` working and installable. New cacheable static assets must be added to the `SHELL` list in `sw.js`.
7. **Self-update must keep working** — do not remove version checks or the update banner flow in `js/pwa.js` / `css/pwa.css`. Clients must still be able to detect a newer `version.json` / waiting service worker and apply an update.
8. **Versions are stamped on `main` only** — `version.json` (and `CACHE_VERSION` in `sw.js`) are generated by `.github/workflows/stamp-version.yml` on push/merge to `main`. Do **not** hand-edit production versions on `main`. Leave feature-branch `version.json` as `"dev"` unless testing stamp behavior. Preserve the `/* CACHE_VERSION: … */` and `const CACHE_VERSION = "…"` markers in `sw.js` so the workflow can patch them.
9. **Match the existing visual language** — Fredoka + Nunito and the landscape-inspired tokens in `css/tokens.css`. Avoid generic purple/glow “AI default” aesthetics unless a redesign is requested.
10. **Mobile + installable** — board/tray must work on small screens; keep PWA install metadata valid.
11. **Testing strategy** — **Playwright is the primary suite** for player flows. Keep a **small unit-test pocket** for pure helpers only. Do not chase high unit coverage of DOM/UI modules.
12. **Dev-only npm** — `package.json` exists for Playwright / test scripts. It must not become a runtime dependency of the game. Never require `npm run build` to ship the app.

Module guidelines:

- **Add a new module** when a feature has a clear boundary (timer, sound, gallery, etc.) rather than stuffing it into `game.js`
- **Keep callbacks injected** across board/tray/pieces so UI modules do not own game state
- **CSS belongs with the feature** — board look in `css/board.css`, not in `chrome.css`
- **Do not “cleanup refactor” unrelated modules** in the same change
- **Prefer pure functions in `js/rules.js` / `js/utils.js` / `js/storage.js`** when logic can be tested without the DOM

## Testing rules

1. **Playwright first** — cover load, correct place, incorrect place, complete small puzzle, shuffle/difficulty in `tests/e2e/`
2. **Unit tests stay small** — only pure modules (`rules`, `utils`, `storage`, and future DOM-free helpers). Do not unit-test `board.js` / `tray.js` / `ui.js` unless logic becomes complex and extracted
3. **Use `data-testid`** for stable selectors; keep them when changing markup
4. **E2E uses `/?e2e=1`** — disables service worker registration for stable tests; exposes `window.__PUZZLE__` for debugging. Do not remove that flag behavior without updating tests
5. **Run before finishing a change that touches game behavior**:
   - `npm run test:unit`
   - `npm run test:e2e` (needs Chromium once: `npx playwright install chromium`)
6. **CI** — `.github/workflows/tests.yml` runs unit + e2e on PRs and `main`
7. **Do not add Jest/Vitest/Testing Library** unless there is a clear need; Node’s built-in test runner is enough for the unit pocket
8. **Do not block on PWA update-banner flakiness** in every PR — optional coverage only; prefer asserting version label + core gameplay

## Versioning & PWA updates

- **`version.json` is authoritative** for the on-screen footer version
- On every push to **`main`** (typically a merged PR), `.github/workflows/stamp-version.yml` writes:
  - `version.json` → `YYYY.MM.DD.<run_number>` plus short SHA / timestamp metadata
  - `sw.js` `CACHE_VERSION` → the same version string (so browsers detect a new worker)
  - commit message includes `[skip ci]` to avoid workflow loops
- Feature branches should keep `"version": "dev"` and `"channel": "development"`
- Update checks run via `js/pwa.js` on load, tab focus, reconnect, and on an interval (compares `version.json` + `registration.update()`)
- When an update is ready, show the update banner; applying it activates the waiting worker (`SKIP_WAITING`) and reloads
- After merge to `main`, wait for the **Stamp version on main** workflow before expecting the production footer version to change

## How the game works today

- Image is sliced into a rectangular grid via CSS `background-position` / `background-size` on piece buttons
- Difficulties: **12 (4×3)**, **24 (6×4)**, **48 (8×6)** — defined in `DIFFICULTIES` in `js/config.js`
- Interaction: **click piece → click board slot**, plus HTML5 **drag-and-drop**
- Correctly placed pieces lock; misplaced pieces can be moved again
- Dropping onto an occupied slot sends the previous piece back to the tray
- Win when every slot holds its matching piece id (`pieceId === slotIndex`) via `js/rules.js`

Piece ids are row-major: `id = row * cols + col`.

## Working practices

1. **Scope tightly** — only change files needed for the task; do not rewrite README or restyle everything casually
2. **Assets** — keep images reasonably sized for the web; put them under `assets/`
3. **Local check** — from repo root: `python3 -m http.server 8080` then open `http://localhost:8080`
4. **Commits** — prefer clear messages that say what the player-facing change is
5. **PRs** — prefer one concern per PR/branch when practical so reviews and merges stay narrow

## Out of scope for now (define later)

Do not implement unless asked:

- Irregular jigsaw piece shapes / interlocking tabs
- Multiple puzzle images / gallery
- Timer, scoring, save/resume via `localStorage`, accounts
- Sound effects, particle-heavy celebrations
- Touch-specific gestures beyond click + drag
