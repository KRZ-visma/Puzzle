# Agent instructions — Puzzle

## Project

Browser-based **interlocking jigsaw** (free-form canvas). Players drag pieces, snap neighbors into groups, and assemble the image on a board silhouette. Hosted as a static **Progressive Web App** on **GitHub Pages**.

Supports large piece counts (up to **1000**). Prefer incremental changes; confirm before another full gameplay redesign.

## Hard rules

These are project constraints. Follow them unless the user explicitly overrides them.

1. **Vanilla web only** — HTML, CSS, and JavaScript for the shipped app. No React/Vue/Svelte, no bundler, no runtime npm dependencies, no required build step to play or deploy.
2. **GitHub Pages static deploy** — keep a working root `index.html` on `main`. Do not move the app behind a build pipeline without being asked.
3. **ES modules** — app code lives under `js/` and loads via `<script type="module">`. Local preview needs HTTP (`python3 -m http.server`), not `file://`.
4. **Browser storage only** — anything that must persist (progress, settings, preferences) uses **`localStorage`** through `js/storage.js` with namespaced keys (`puzzle:…`). No backend, database, accounts, or cloud sync unless explicitly requested.
5. **Stay modular to reduce merge conflicts** — put new concerns in their own modules/CSS partials. Do not re-merge everything into one giant `game.js` or `styles.css`. Touch the fewest files needed for the task.
6. **Remain a PWA** — keep `manifest.webmanifest`, icons, and root `sw.js` working and installable. New cacheable static assets must be added to the `SHELL` list in `sw.js`.
7. **Self-update must keep working** — do not remove version checks or the update banner flow in `js/pwa.js` / `css/pwa.css`. Clients must still be able to detect a newer `version.json` / waiting service worker and apply an update.
8. **Versions are stamped on `main` only** — `version.json` (and `CACHE_VERSION` in `sw.js`) are generated by `.github/workflows/stamp-version.yml` on push/merge to `main`. Do **not** hand-edit production versions on `main`. Leave feature-branch `version.json` as `"dev"` unless testing stamp behavior. Preserve the `/* CACHE_VERSION: … */` and `const CACHE_VERSION = "…"` markers in `sw.js` so the workflow can patch them.
9. **Match the existing visual language** — Fredoka + Nunito and the landscape-inspired tokens in `css/tokens.css`. Avoid generic purple/glow “AI default” aesthetics unless a redesign is requested.
10. **Mobile + installable** — playfield must work on small screens (Pointer Events); keep PWA install metadata valid.
11. **Testing strategy** — **Playwright is the primary suite** for player flows. Keep a **small unit-test pocket** for pure helpers only. Do not chase high unit coverage of DOM/canvas modules.
12. **Dev-only npm** — `package.json` exists for Playwright / test scripts. It must not become a runtime dependency of the game. Never require `npm run build` to ship the app.
13. **New functionality includes tests in the same change** — if you add or change player-facing behavior or pure logic, you must update or add tests before finishing:
    - Player-facing / UI flow → Playwright in `tests/e2e/`
    - Pure helper / rules / geometry / snap / groups / storage logic → unit test in `tests/unit/`
    - Both when both apply
    - Docs-only, pure styling with no behavior change, or chore-only work may skip new tests; say so in the PR
    - Do not merge behavior changes that leave existing tests failing
14. **Canvas engine for scale** — piece rendering and hit-testing use the Canvas 2D API (`Path2D`, `isPointInPath`). Do not regress to per-piece DOM nodes for large difficulties.

Module guidelines:

- **Add a new module** when a feature has a clear boundary (timer, sound, gallery, etc.) rather than stuffing it into `game.js`
- **Keep canvas I/O in `playfield.js`**; keep snap/group/geometry pure and unit-tested
- **CSS belongs with the feature** — playfield look in `css/playfield.css`, not in `chrome.css`
- **Do not “cleanup refactor” unrelated modules** in the same change
- **Prefer pure functions in `js/geometry.js` / `js/groups.js` / `js/snap.js` / `js/rules.js` / `js/utils.js` / `js/storage.js`** when logic can be tested without the DOM

## Testing rules

1. **New behavior ⇒ tests in the same PR/commit set** (see hard rule 13). Treat “feature without tests” as incomplete work.
2. **Playwright first** — cover player flows in `tests/e2e/` (load, assemble, connect neighbors, solve, shuffle/difficulty, large piece init). Canvas drags are awkward in CI; prefer `window.__PUZZLE__` helpers (`assemblePiece`, `connectNeighbors`, `solve`) for placement assertions while still checking visible chrome.
3. **Unit tests stay small** — only pure modules (`geometry`, `groups`, `snap`, `rules`, `utils`, `storage`, `progress`, `rng`). Do not unit-test `playfield.js` / `ui.js` unless logic becomes complex and extracted.
4. **Use `data-testid`** for stable selectors; add them with new interactive UI; keep them when changing markup.
5. **E2E uses `/?e2e=1`** — disables service worker registration for stable tests; exposes `window.__PUZZLE__` for debugging. Do not remove that flag behavior without updating tests.
6. **Definition of done for a behavior change**:
   - Implement the feature in the right module(s)
   - Add/update tests
   - Run `npm run test:unit` and `npm run test:e2e` locally (Chromium once: `npx playwright install chromium`)
   - CI green on the PR (`.github/workflows/tests.yml`)
7. **CI also checks that behavior-file diffs include test diffs** — unless the PR body contains `tests-not-required` with a short reason.
8. **Do not add Jest/Vitest/Testing Library** unless there is a clear need; Node’s built-in test runner is enough for the unit pocket.
9. **Do not block on PWA update-banner flakiness** in every PR — optional coverage only; prefer asserting version label + core gameplay.

## Versioning & PWA updates

- **`version.json` is authoritative** for the on-screen footer version
- On every push to **`main`** (typically a merged PR), `.github/workflows/stamp-version.yml` writes:
  - `version.json` → `YYYY.MM.DD.<run_number>` plus short SHA / timestamp metadata
  - `sw.js` `CACHE_VERSION` → the same version string (so browsers detect a new worker)
  - commit message includes `[skip ci]` to avoid workflow loops
- Feature branches should keep `"version": "dev"` and `"channel": "development"`
- Update checks run via `js/pwa.js` on load, tab focus, reconnect, and on an interval (compares `version.json` + `registration.update()`)
- When an update is ready, show the update banner; applying it activates the waiting worker (`SKIP_WAITING`) and reloads
- After merge to `main`, wait for the **Stamp version on main** workflow before expecting the production footer version to change

## How the game works today

- Pieces are interlocking shapes (cubic Bézier tabs/blanks) from a shared edge map in `js/geometry.js`
- Drawn on a single canvas with `Path2D` clipping + `drawImage`; hit-testing uses `isPointInPath`
- Difficulties: **12**, **48**, **100**, **500**, **1000** — defined in `DIFFICULTIES` in `js/config.js`
- Interaction: **Pointer Events** drag; releasing near a neighbor or the board silhouette snaps and may merge groups
- Groups move as a unit; progress counts pieces locked to their solved board seats
- Win when every piece sits on its solved seat (`js/snap.js` / `js/rules.js`)

Piece ids are row-major: `id = row * cols + col`.

## Working practices

1. **Scope tightly** — only change files needed for the task; do not rewrite README or restyle everything casually
2. **Assets** — keep images reasonably sized for the web; put them under `assets/`
3. **Local check** — from repo root: `python3 -m http.server 8080` then open `http://localhost:8080`
4. **Commits** — prefer clear messages that say what the player-facing change is
5. **PRs** — prefer one concern per PR/branch when practical so reviews and merges stay narrow

## Out of scope for now (define later)

Do not implement unless asked:

- Timer, scoring, accounts
- Sound effects, particle-heavy celebrations
- Pinch-zoom / pan camera for very dense boards
- WebGL / OffscreenCanvas worker pipelines (Canvas 2D is the current target)
